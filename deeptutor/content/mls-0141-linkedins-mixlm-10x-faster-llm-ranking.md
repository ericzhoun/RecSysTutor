# TL;DR

LinkedIn released details on MixLM, a production ranking system that addresses the latency bottleneck of using LLMs for search.

By replacing long textual item descriptions with pre-computed "soft embedding" tokens, they reduced inference context length by orders of magnitude (from ~900 tokens to ~2 tokens per item).

This allowed them to deploy LLM-based reranking to 100% of job search traffic, yielding a 10x throughput increase and a 0.47% DAU lift compared to previous baselines.

# Introduction

The standard hierarchy of information retrieval embedding-based retrieval (bi-encoders) for candidate generation, followed by cross-encoder reranking hits a wall when you try to introduce LLMs at the reranking stage.  
  
While LLMs are superior relevance judges, using them as cross-encoders is prohibitively expensive. Concatenating a user query with a full document (or job description) creates a massive context window. Since attention complexity is quadratic, running this for hundreds of candidates per request blows up latency budgets.

Most teams compromise by using smaller models or aggressively truncating text, which hurts performance.  
  
LinkedIn’s recent paper, "MixLM," proposes a middle ground: "Text-Embedding Mix-Interaction."

Instead of feeding raw text to the Ranker LLM, they feed it a highly compressed embedding representation of the document, injected directly into the LLM’s input layer.

#   
The Mechanics: Replacing Text with Soft Tokens  

[](../assets/9ddeb165364cf064.png)

The core architecture consists of two models: an Encoder LLM and a Ranker LLM.  
  
In a traditional setup, you prompt the model with:  
System Prompt + Query + Item Description  
  
In MixLM, the prompt becomes:  
System Prompt + Query + Item Embeddings  
  
The "Item Embeddings" are not standard output embeddings from a BERT model.

They are "soft tokens" generated by the Encoder LLM.

The Encoder takes the full item text, processes it, and outputs a condensed dense vector (or a few vectors). These vectors are stored in a nearline cache.  
  
At inference time, the serving system retrieves these pre-computed embeddings and concatenates them with the token embeddings of the live user query. The Ranker LLM then processes this mixed input.  
  
The compression ratio is extreme. In their experiments, they compressed median document lengths of 900 tokens down to just 1 or 2 embedding tokens.

This effectively eliminates the "Item" component of the attention cost, shifting the computational load almost entirely to the query processing.

# The Training Recipe: Forcing Alignment

The challenge with mixing text tokens and dense embeddings is alignment.

The Ranker LLM needs to "understand" that a specific dense vector represents a specific job description.

You cannot simply plug an embedding from Model A into the input layer of Model B.  
  
The authors solved this with a three-stage training pipeline culminating in joint optimization:  
  
**Domain Fine-Tuning:** They SFT a base model on domain-specific reasoning data.  
**Teacher Training** : They train a standard, text-only cross-encoder to act as the ground-truth teacher.  
**Joint Encoder-Ranker Training** : This is the novel part. They co-train the Encoder and Ranker using a curriculum learning strategy.  
  
They utilize a "Self-Alignment Loss." 

During training, they pass both the full text (Teacher) and the mixed embeddings (Student) through the model.

They force the hidden states of the Ranker (driven by embeddings) to match the hidden states of the Teacher (driven by text). 

This ensures the compressed embeddings trigger the same semantic activations in the Ranker as the original text would have.

# Production Implications

The engineering wins here are significant for anyone managing high-throughput search systems.  
  
**1\. Latency Reduction via Cache**  
Because the item representations are pre-computed offline/nearline, the online inference cost for the "item" portion of the prompt effectively vanishes.

The model only has to process the query tokens and attend to a tiny handful of item tokens.

This reduced the computational footprint enough to allow full-traffic deployment, a rarity for LLM-based rerankers in 2025.  
  
**2\. Shared-Prefix Optimization**  
The paper highlights a specific optimization in the serving layer (using SGLang). Since the Query is identical for all candidate items in a single request, the KV cache for the System Prompt and Query is computed once and shared across the batch. Combined with the compressed item embeddings, the marginal cost of scoring an additional candidate becomes trivial.  
  
**3\. Prefill-Only Inference**  
Since this is a ranking task (outputting a relevance score), there is no generative decoding phase. The system runs a forward pass to the final token and extracts the logit for a "Yes/No" token.

The authors optimized their serving engine to dump the KV cache immediately after the prefill phase, significantly reducing VRAM pressure and increasing batch sizes.  
  
**4\. Performance vs. Efficiency**  
They achieved a 10x throughput improvement compared to a summarized-text baseline. While the pure text-based teacher model still holds a slight edge in raw NDCG metrics (0.9432 vs 0.9239), the drop is minimal compared to the efficiency gains.

More importantly, the system outperformed existing production baselines (embedding retrieval and lightweight rerankers), leading to the 0.47% increase in Daily Active Users.  

  
This paper validates a growing trend in ML infrastructure: moving complexity offline. By compressing semantic information into dense vectors that are native to the LLM's latent space, we can decouple the cost of "reading" the document from the cost of "ranking" it.
