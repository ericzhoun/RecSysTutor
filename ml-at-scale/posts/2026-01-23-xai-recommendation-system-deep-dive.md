The pipeline executes a standard four-stage lifecycle: Query hydration → Retrieval → Filter → Rank</p><p>The defining characteristic of the system is the removal of explicit feature engineering in favor of raw embedding interoperability.The system does not “calculate” features; it looks up pre-computed vectors and passes them to a distilled Grok model.</p><p>Another interesting point is the lack of a prescorer, they chose to optimize for a better feed vs latency. </p><p>In the end of the newsletter, I will comment in depth based on my experience as an MLE.</p><h1>Query Hydration</h1><p>The recommendation request begins with the RecommendationRequest struct in Rust. This is not a simple database lookup; it is a parallelized gather-and-scatter operation to build the <strong>User Context</strong>.</p><p>The system hits the User Data Store to build a composite view of the user’s current state.</p><ol><li><p><strong>User Embedding:</strong> A dense float-vector (d=2048) representing the user’s long-term interests. This is pre-computed by a separate offline User Tower and stored in a low-latency KV store.</p></li><li><p><strong>Real Graph State:</strong> The system retrieves the user’s weighted social graph. Unlike a standard follower list, this contains interaction coefficients, specifically identifying the “Core Network” (users with &gt;0.8 interaction probability).</p></li><li><p><strong>Anti-Signals:</strong> A Bloom filter or hash set of recent “Dislikes,” “Mutes,” and “Show Less” actions. This is loaded early to short-circuit retrieval paths later.</p></li></ol><p>If the User Embedding fails to load, the request is terminated immediately.</p><p>The architecture treats the embedding as the primary key for the entire session.</p><h1>Retrieval</h1><p>The system targets a retrieval pool of roughly 1,500 to 2,000 candidates per request. This comes from two distinct, concurrent sources.</p><p><strong>1. Source: Thunder (In-Network / Real Graph)</strong><br>Thunder is the graph processing engine. It executes a breadth-first search on the user’s “Core Network.”</p><ul><li><p><strong>Mechanism:</strong> It iterates over the top users the requestor interacts with.</p></li><li><p><strong>Time Window:</strong> It creates a window of recent posts (typically &lt;24h, tighter for high-velocity users).</p></li><li><p><strong>Logistic Regression Lite:</strong> The retrieved posts undergo a lightweight scoring pass (a linear combination of author_weight and time_decay) to cap the retrieval at ~1,000 candidates.</p></li></ul><p><strong>2. Source: Phoenix (Out-of-Network / Vector Search)</strong><br>Phoenix is the ANN (Approximate Nearest Neighbor) engine. It solves the embedding retrieval problem.</p><ul><li><p><strong>Algorithm:</strong> It uses HNSW (Hierarchical Navigable Small World) graphs to index the vector space of all recent tweets.</p></li><li><p><strong>Query:</strong> It queries the index using the <strong>User Embedding</strong> from the hydration step.</p></li><li><p><strong>Optimization:</strong> The search is sharded. The index is likely segmented by language and safety clusters to prune the search space immediately. It returns the top ~1,000 candidates that act as “nearest neighbors” to the user’s interest vector.</p></li></ul><h1>Post Hydration</h1><p>At this stage, the system has a list of ~2,000 Candidate IDs.</p><p>The system performs a massive multi-get request to the Tweet Store:</p><ul><li><p><strong>Content Embeddings:</strong> The critical payload. The system fetches the pre-computed embedding for the tweet text and any attached media (Video/Images are projected into the same latent space).</p></li><li><p><strong>Interaction State:</strong> Real-time counters (Likes, Reposts, Replies). These are not used as raw integers but are often log-normalized and bucketed before entering the model.</p></li><li><p><strong>Author Features:</strong> The embedding of the author is fetched to compute the dot-product similarity between User_Vector and Author_Vector as an input signal.</p></li></ul><h1>Filters</h1><p>Before the compute-heavy ranking, the candidate list passes through a chain of boolean predicates (Filters).</p><ol><li><p><strong>Visibility Filter:</strong> Checks the bi-directional block graph. If Candidate A blocked User B (or vice versa), drop.</p></li><li><p><strong>Safety Filter:</strong> Enforces the user’s specific sensitivity settings. It checks the content labels (e.g., label:nsfw_high_precision).</p></li><li><p><strong>Feedback Fatigue Filter:</strong> Checks the “Anti-Signals” loaded during Query Hydration. If the user clicked “Show Less” on this author or this topic cluster within the last session, the candidate is dropped.</p></li><li><p><strong>Social Proof Filter:</strong> In specific “For You” configurations, the system enforces a minimum engagement threshold (e.g., “Must have &gt;5 likes”) to prevent cold-start spam from entering the heavy ranker.</p></li></ol><h1>Scoring</h1><p>The filtered candidates are batched and sent to the <strong>Heavy Ranker</strong>. This is the most expensive component in the stack.</p><p>The model is a JAX-based Transformer (a distilled version of the Grok architecture).</p><p>It treats recommendation as a sequence modeling problem.</p><ul><li><p><strong>Input:</strong> [User_Context_Tokens] [Candidate_1_Tokens] ... [Candidate_N_Tokens]</p></li><li><p><strong>Output:</strong> A probability distribution over a set of engagement actions (P(Like), P(Reply))</p></li></ul><p>This is a Multi-Task Learning (MTL) structure, with one head for each prediction.</p><h1>Personal deep dive</h1><p><strong>1. Production Ranker Size vs. Latency</strong><br>The codebase hides the massive operational cost here.</p><p>Standard industry practice (Meta, TikTok) typically involves a three-step funnel: </p><p>Retrieval (10k) → Light Ranker (2k) → Ranker (500)<br><br>X has removed the middle step. They are feeding ~1,500 candidates directly into a Transformer-based ranker.</p><p>This is computationally wildly expensive. Unless they have infinite TPU budget, they are likely running a smaller, quantized model than they admit, or their “Grok” ranker is heavily distilled. Without a prescorer to cull the “obviously bad” 50% of candidates cheaply, this is expensive and <strong>most importantly high latency</strong>.</p><p><strong>2. Transformer Heads: Standard but opaque</strong></p><div class="paywall-jump" data-component-name="PaywallToDOM"></div><p>They use a Multi-Task Learning (MTL) head structure (one head for Likes, one for Replies, one for Dwell Time).<br>While standard, the magic isn’t in the heads but it’s in the loss weights.</p><p>X likely tunes these weights daily to manipulate the platform vibe. If they want to kill “rage-bait,” they can zero out the weight.</p><p>We can see the structure, but we can’t see the policy driving the weights.</p><p><strong>3. Hydration System: The “Distributed Monolith” Risk</strong><br>The move to Rust ensures type safety, but it doesn’t solve network physics.</p><p>The system requires real-time hydration from the User Store, Tweet Store, Safety Store, and Graph Store.<br>If <em>any</em> of these services has problems, does the ranker fail open or closed?</p><p>If the “Safety Store” has 50ms latency, the whole feed stalls?</p><p><strong>4. No Feature Engineering: The Black Box</strong><br>They deleted the code that calculates manual features (e.g., “is_shopping_video”). The model learns purely from embeddings.<br>The preference is baked into the vector space. To fix a ranking bias, you might have to retrain the entire upstream embedding model or the ranker itself.</p><p>They traded code complexity for interpretability.</p><p><strong>5. A/B Testing: The Missing Infrastructure</strong><br>The GitHub repo shows a Scorer trait, which allows swapping models.<br>The actual experimentation infrastructure is completely missing. Real-world A/B testing requires “Shadow Scoring” (running Model B silently alongside Model A to compare results without serving them).</p><p>There is no evidence of shadow pipelines in the public code. What we are seeing is likely a sanitized “happy path,” not the messy, complex routing logic required to test models on 500M users.</p><p><strong>6. Why No Prescorer?</strong></p><p>As mentioned in point 1, the lack of a prescorer is the most controversial architectural choice.<br>They are betting everything on the quality of the Vector Search.</p><p>They assume the ANN index only returns “good” candidates. If the Vector Search quality degrades (e.g., returning irrelevant spam that happens to be close in vector space), the Heavy Ranker wastes 100% of its time processing noise. This puts immense pressure on the upstream embedding quality.</p><p><strong>7. Scaling the Two-Tower System</strong><br>The “Two-Tower” model (User Tower + Candidate Tower) is standard, but scaling it to X’s velocity is unsolved in the public docs.<br><br>How do they handle the “Cold Start” problem for new tweets?</p><p>Computing an embedding for a tweet takes non-zero time.</p><p>There is likely a significant lag (seconds to minutes) between a tweet being posted and it becoming available in the Vector Index. This means the “For You” feed is likely blind to breaking news until the indexing pipeline catches up, whereas the “Following” feed is instant.</p><p>Are they really searching across ALL tweets? If yes, I am quite shocked!</p><h1>References</h1><ol><li><p><a href="https://github.com/xai-org/x-algorithm">xai-org x-algorithm</a></p></li><li><p><a href="https://deepwiki.com/xai-org/x-algorithm">DeepWiki x-ai algorithm</a></p></li></ol><p></p><p></p><p></p>
